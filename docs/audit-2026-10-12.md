## High

### H1. Nothing stops two instances from changing the system at the same time. Open.
- **Where:** `src/Optimizer.App/Services/ChangeGate.cs:10-12`, `ChangeRunner.cs`, `src/Optimizer.Core/Tweaks/TweakEngine.cs:315-384`.
- **Verified:** there is no `Mutex`, `EventWaitHandle` or single-instance check anywhere in `src`, and `ChangeGate` only works inside one process.
- **How it happens:**
  - the GUI plus `--apply` or `--undo-all`
  - two accounts running the elevated exe; the data folder is shared by every account
- **Failure:** instance A reads "no backup" (line 318), and instance B does the same before A saves. A saves and applies. B then records the already changed value as its original (line 365) and saves over A's file (line 384). The real original is lost. The window is short, but nothing can repair the loss.
- **Second effect:** a second start also empties `temp\` (`ProcessHardening.UseTempFolder`, `ProcessHardening.cs:143-160`) while the first instance's DISM or winget may be using it.
- **Fix:**
  - A named mutex `Global\Tunero.Changes` around apply, undo, update, uninstall and the temp cleanup.
  - The CLI waits, or exits with its own code.
  - Handle `AbandonedMutexException`.
  - Release the mutex before the update or the package-manager handoff ends the app.

### H2. Running the tests can move the real data folder. Open.
- **Where:** `tests/Optimizer.Core.Tests/TestSetup.cs:10`, `src/Optimizer.Core/Logging/Log.cs:16-17`, `src/Optimizer.Core/Platform/DataPaths.cs:23-24, 33-48`.
- **Verified chain:**
  1. The module initializer calls `Log.DisableFile()`.
  2. That runs `Log`'s static initializer, which reads `DataPaths.Logs`.
  3. That runs `ResolveRoot`, which calls `Directory.Move(legacy, root)` when a `PCOptimizer` folder exists and no `Tunero` folder does.
- **Failure:**
  - On a PC that still has `%LocalAppData%\PCOptimizer`, `dotnet test` renames the real folder with its backups. With an elevated run, as CONTRIBUTING suggests, the same happens to `%ProgramData%\PCOptimizer`.
  - An installed 0.7.3 or older then no longer finds its undo data.
  - This breaks the first rule in CLAUDE.md, and `ArchitectureTests` cannot see it.
- **Fix:**
  - Make `DataPaths.Root` and `Log.Directory` lazy and free of side effects.
  - Move the migration into an explicit `DataPaths.MigrateLegacy()`, called from `Program.Main` before `SecureFolder.PrepareRoot`.
  - Let the test module initializer point the root at a temp folder.

### H3. The Startup page can switch any Microsoft auto-start service to Manual. Open.
- **Where:** `src/Optimizer.Core/Startup/StartupScanner.cs:216, 226, 438`, `src/Optimizer.App/ViewModels/PageViewModels2.cs:48`.
- **Verified:**
  - Every service with Start=2 gets `Enabled = true` (line 226).
  - `StartupTweaks.Set` turns it into `ServiceAction { StartType = Manual }` (line 438) without checking the publisher.
  - The Services page makes unknown Microsoft services read-only (`ServiceManager.cs:61`). The Startup page does not.
- **Failure:**
  - In Expert mode, Dhcp, Dnscache, BFE, MpsSvc, EventLog or AudioSrv can be switched off.
  - After the change, the service no longer matches `start != 2` (line 216). Its row disappears, and the Startup page offers no way back.
  - Undo on the Changes page still restores it, because the change has a backup.
- **Fix:**
  - In `StartupTweaks.Set`, return null for Microsoft-signed services the service catalog does not mark `manualOk`, using the same rule as `ServiceRow.Edit`.
  - List services the app set to Manual (from the backups), so they can be switched back on the Startup page.

### H4. Elevated Chocolatey inherited `ChocolateyInstall` from the user's environment. Fixed in 0.8.0.
- **Where:** `PackageInstall.HardenChocolateyEnvironment` (`PackageInstall.cs:100-105`).
- **What changed:** it removes every `Chocolatey*` variable and sets `ChocolateyInstall` to the checked root. It runs on both the update and the uninstall path (`MainViewModel.cs:821`) and is tested (`PackageInstallTests.cs:86`).
- **What is left, at lower severity:**
  - The fix sits in the caller rather than in `ProcessHardening`.
  - choco still runs through an elevated PowerShell, which receives M2's leftover variables.
  - choco's subfolders (`extensions\`, `helpers\`, `hooks\`, `config\`) are not checked.

### H5. The uninstall deletes the data folder even when the package manager failed or Tunero was started again. New in pass 2.
- **Where:** `src/Optimizer.Core/Platform/SelfUninstall.cs:22-40`, `src/Optimizer.App/ViewModels/MainViewModel.cs:913-955`.
- **Verified:**
  - The app starts the package manager's window (line 917), then starts the cleanup script (line 936), then shuts down.
  - The script waits for processes named Tunero, `-Timeout 60`. For Chocolatey it also waits for the window, `-Timeout 900`.
  - After that it runs `rd /s /q` on the data folder no matter what happened.
  - Nothing tells the script whether `choco uninstall` or `winget uninstall` succeeded.
  - After the waits it never checks whether Tunero is running again.
- **Failure:**
  - The user uninstalls and keeps their changes, and the package manager fails (a network error, or a choco failure message left open). Tunero stays installed with no backups, and its changes can no longer be undone.
  - A user who starts Tunero again before the cleanup runs, or more than 60 seconds into a Tunero that will not exit, loses the backups that instance creates. Only files that are open survive.
- **Fix:**
  - Run the cleanup in the package manager's own script, after the package manager, and only when `$ok` is true.
  - Before each `rd`, stop if `Get-Process -Name` finds Tunero running again.
  - For a downloaded copy, keep the current script but add the same running check.

## Top 5 refactors (re-ranked after pass 2)

### 1. A cross-process change lock (H1)
- **Scope:** `Program.cs`, `ChangeRunner.cs`, `CommandLineApply.cs`, `ProcessHardening.UseTempFolder`, and the update and uninstall paths in `MainViewModel`.
- **Why:** it closes a path that loses originals, and the change is small.
- **Risk:** low. Release the mutex before the update or the package-manager handoff ends the app, and treat an abandoned mutex as free.

### 2. One uninstall and update handoff that respects the outcome (H5, M23, M29), as `UpdateService` and `UninstallService`
- **Scope:** `SelfUninstall`, the package-manager section of `PackageInstall`, `MainViewModel.cs:680-960`.
- **What:** one PowerShell script per run that:
  - waits for the app
  - runs the package manager
  - checks `$ok`, and for updates the installed version
  - removes the data folder only on success, and only when no Tunero runs
  - restarts the app with the right text
- **Why:** this fixes the new high finding and two mediums, and takes about 300 lines out of `MainViewModel` into testable services.
- **Risk:** medium. `PackageInstallTests` and `SelfUninstallTests` pin the exact script strings, and the flow needs a VM run per package manager.

### 3. Remove the side effects from `DataPaths` and enforce the test guard by construction (H2, M5)
- **Scope:** `DataPaths.cs`, `Log.cs`, `Program.cs`, `TestSetup.cs`, `ReadOnlyContext.cs`, `ArchitectureTests.cs`, CONTRIBUTING.
- **What:**
  - The migration runs explicitly at startup, and tests use a temp root.
  - The read-only runner uses an allowlist of commands.
  - An architecture test scans `src/` for direct process starts.
- **Risk:** medium. The startup order has to stay "move, then secure".

### 4. One hardened `ProcessLauncher` plus a `Platform/PowerShellScript` builder (M2, M22, cross-cutting duplication)
- **Scope:**
  - `SystemProcessRunner`, `StreamingProcess`, `StabilityProbe`, `Programs`
  - the four `MainViewModel` launches, including the unhardened restart at `:766`
  - `PackageInstall`, `SelfUninstall`, `WingetPackage`
- **What:** one place for:
  - the powershell path, quoting and the `Run` template (with the `$?` check for winget too)
  - timeouts and OEM decoding
  - the environment: `Chocolatey*`, the known-folder variables, `__COMPAT_LAYER`
  - refusing cmd metacharacters
- **Risk:** medium. Keep each caller's timeout and streaming behavior; `SecurityTests` cover most of it.

### 5. One release-verification script and one package-info file (M24, M25, M31, the packaging-facts low)
- **Scope:**
  - `scripts/verify-release.ps1`, used by `winget.yml`, `chocolatey.yml` and the three manifest scripts
  - `scripts/package-info.psd1`: id, repository, summary, tags, minimum OS
  - Scoop manifests pushed from a workflow instead of `autoupdate`
  - a test that every workflow signs and checks the same statement
- **Why:** low cost, it closes the unsigned-hash path for Scoop, and it stops the five product descriptions drifting apart.
- **Risk:** low. Keep the Chocolatey pin on the verified hash.
