# Repository audit and 1.0 readiness, 2026-10-13

Main at `8276863` (version 0.9.15), plus uncommitted work from another session in `Actions/` (ActionContext, DohActions, ExtendedActions, SystemActions), `Platform/` (DeElevatedLauncher, StartMenuShortcut, SystemApi, new ShellLinkFile and TaskSchedulerCom), `Startup/StartupScanner.cs` and five test files. Findings in that work are tagged **[WIP]**.

The question for this audit: what does Tunero need to leave preview and ship as 1.0, and what does it need to make its claim true, "Built to be the only PC optimizer you need" (README.md:5, website) and "Built to replace a folder full of tools" (website/src/i18n/en.ts:117)?

**Method.** Seven reviewers read the code in parallel:
- five areas, file by file: core engine; platform, hardware and checks; feature modules and the update path; WPF app; tests, CI, catalog data, docs and website
- one cross-cutting reviewer for architecture, coupling and dependencies
- one product reviewer who compared the app with the 17 tools in the local feature reference and `docs/feature-gap-analysis.md`

Each reviewer started from `docs/audit-2026-10-12.md` and the fix commit `8dc78c1`, and reported only new findings or findings that are still open. I re-read the code behind every high finding and every medium marked as a 1.0 blocker, and dropped what I could not confirm. The other mediums and lows come from the reviewers and were spot-checked only. "(unverified)" marks findings that depend on behavior nobody could check here, such as how Windows or antivirus reacts.

**Baseline.** `dotnet build -c Release` builds with 0 warnings and 0 errors, and `dotnet test -c Release --filter "Category!=Hardware"` passes all 927 tests. No code was changed for this audit.

## Summary

**The code is close to 1.0. The claims and the proof are not.** The apply and undo engine, the update chain, SafeDelete, the elevation boundary and the catalog rules held up again. Most of yesterday's audit is fixed: the cross-process change lock, `DataPaths` without side effects, safe uninstall, the Startup service rule, update hardening and the multi-commit CI check.

1.0 is held back by four things:
1. **A promise about the future that nothing enforces.** Undo has to keep working across every later update, but the backup format has no version, and no test loads a backup written by a released version (H3).
2. **Two real bugs:**
   - Import applies only the first of its one-by-one changes (H1).
   - Ryzen AI 300 laptops are treated as two-chiplet X3D processors, which gives wrong advice and untrue block reasons (H2).
3. **Claims ahead of the evidence:**
   - Home edition and 24H2/25H2 are claimed but never tested (H4).
   - winget and Chocolatey install commands are shown, but neither package is live.
   - "Undo everything" is said where removed apps and deleted files are the exception.
   - The README's test banner describes more than the tests cover.
4. **Fail-safe gaps that a 1.0 user will hit sooner or later:**
   - A failed update restart leaves no runnable exe.
   - A failed read during apply still says "Applied".
   - A hung probe hides most checks.
   - A failed scan is never shown.
   - Windows' own COM-handler logon tasks can be switched off from the Startup page.

**The promise is about 70 % true today.** Tunero can replace these tools for most users:
- the tweak and privacy tools: O&O ShutUp10++, Win11Debloat, WinUtil's tweak part, CrapFixer, Sophia Script, RemoveWindowsAI
- most of AtlasOS and ReviOS, leaving out on purpose what lowers security

It cannot yet replace these:
- **Bulk Crap Uninstaller:** no bulk or quiet uninstall, no leftover scan.
- **Process Lasso:** start priorities only, and still unproven.
- **Autoruns:** several locations missing, no delete, no export.
- **WinUtil's installer:** 34 entries against 236.
- **DDU and NVCleanstall:** out of scope; Tunero only links to them.

The largest gaps are listed under "Promise gaps" below, with effort and constraints.

## High

### H1. Import applies only the first of its one-by-one changes.
- **Where:** `src/Optimizer.App/ViewModels/MainViewModel.Transfer.cs:79-84`, with `MainViewModel.cs:208, 570-572, 1164, 1507` and `Services/ChangeRunner.cs:85, 151`.
- **How it happens:**
  1. `ChangeRunner.ApplyAsync` raises `Changed` inside its exclusive section (line 151).
  2. The handler `Runner.Changed += async (_, t) => await OnChangedAsync(t)` runs synchronously up to its first await: `AfterChangeAsync`, then `ScanAsync`, then `ScanOnceAsync`, which sets `IsScanning = true` (line 1164).
  3. `OnIsScanningChanged` sets `ChangeGate.Instance.Scanning = true` before `ApplyAsync` returns.
  4. The next pass of `foreach (var t in plan.OneByOne) await Runner.ApplyAsync(t);` finds `!ChangeGate.Instance.CanChange` (`ChangeRunner.cs:85`) and reports "Change_Busy".
- **Failure:**
  - An exported file with two or more Expert, Preview, anti-cheat or boot-critical tweaks applies only the first one. The rest each show "Wait until the current change or scan has finished".
  - The first one is refused too when the user answers the one-by-one question while the rescan after the batch is still running.
  - `NetworkViewModel.ChooseDnsAsync` (`PageViewModels.cs:353`) already works around the same race.
- **Fix:**
  - `await ScanInProgress` (or `Owner.ScanAsync()`) before each `Runner.ApplyAsync` in the loop.
  - Better: when a scan is the only blocker, let `ExclusiveAsync` wait for it instead of refusing, so every chained flow is safe.
  - Add a `ChangeRunner` test with fake dialogs.
- **1.0 blocker:** yes.

### H2. Ryzen AI 300 (Strix Point) is classified as a two-chiplet X3D processor.
- **Where:** `src/Optimizer.Core/Findings/Checks/CpuPowerChecks.cs:62-63`, `Catalog/Data/cpu.json` (`"x3dAsymmetryFactor": 2.0`).
  ```csharp
  var sizes = cpu.L3Domains.Select(d => d.SizeBytes).Where(s => s > 0).ToList();
  if (sizes.Count >= 2 && sizes.Max() >= c.Cpu.X3dAsymmetryFactor * sizes.Min()) return X3dLayout.MultiCcdAsymmetric;
  ```
- **How it happens:** the topology test runs before any name check. A Ryzen AI 9 HX 370 or 365 has a Zen 5 cluster with 16 MB of L3 and a Zen 5c cluster with 8 MB. Two L3 domains with 16 at least 2.0 times 8 give `MultiCcdAsymmetric`.
- **Failure:** on a common laptop and mini PC processor, the app states things that are untrue:
  - `cpu.x3dMultiCcd` becomes true, so High performance and Ultimate are blocked with "Ryzen X3D with two chiplets needs the Balanced plan".
  - Game Mode is rated up with the X3D reason.
  - Removing Xbox Game Bar is guarded.
  - F10.x3d reports a Problem with impact 4 when the plan is not Balanced.
  - F15.amdChipset shows its X3D variant.
- **Fix:**
  - Run the topology test only when the name contains "X3D"; keep the model lists as the fallback.
  - Add a test with a 16 MB plus 8 MB layout and the name "AMD Ryzen AI 9 HX 370".
- **1.0 blocker:** yes (the honest-content rule).

### H3. Backups have no format version, and nothing tests that backups from released versions still restore.
- **Where:**
  - `src/Optimizer.Core/Backup/BackupStore.cs:27-59`: `TweakBackup` has `AppVersion` and `CatalogVersion`, but no format field.
  - `Actions/TweakAction.cs:62-84`: 22 `[JsonDerivedType]` discriminators.
  - `Tweaks/TweakEngine.cs:627-641`.
  - `Tweaks/TweakCatalog.cs:30`.
- **Verified:**
  - No test reads a backup file written by an earlier version. The "legacy" case in `UndoTests.cs:146-147` serializes a `TweakBackup` built with today's types.
  - A stored action that no longer deserializes to the same target is dropped with a log line only:
    ```csharp
    return a?.TargetKey == entry.TargetKey ? a : null;
    ...
    Log.Warn("engine", $"stored action of {entry.TargetKey} unreadable: {ex.Message}");
    return null;
    ```
  - `TweakCatalog.Version = "2026.10.3"` ("bumped whenever catalog content changes") was last changed in `73d8bea`. 16 commits have changed `Catalog/Tweaks` since, so every backup records a stale value.
- **Failure:** what can break undo for everyone who applied with an earlier version:
  - renaming a property, an enum member or a discriminator
  - changing a `TargetKey` format: `reg:`, `regbits:`, `pwr:{scheme}:{sub}:{set}`, `nic:`, `doh:`
  - changing a `StoredValue` encoding: `missingKeys:N`, `raw:N`, `scheme;ac;dc`, `scheme-created`

  Undo then falls back to "cannot be restored automatically". Nothing fails in CI. A 1.0 that promises undo across updates cannot refactor its action classes safely without this.
- **Fix:**
  - Add `Format = 1` to `TweakBackup` and `PendingUndo`; refuse a newer format, as `ChangeTransfer.Parse` already does.
  - Commit golden backup files under `tests/Optimizer.Core.Tests/Fixtures/backups/`: one per action type, plus a runtime `Definition` and a pending undo. Generate them from v0.9.x now and add v1.0.0 files at release. A test loads, resolves and reverts each one in the sandbox.
  - Pin the discriminators and target key formats in a test.
  - Write the rule in CONTRIBUTING: never rename or remove them.
  - Derive the catalog version from a hash of the embedded catalog, or delete it.
- **1.0 blocker:** yes.

### H4. The supported Windows versions and editions are claimed, not tested.
- **Where:** README.md:7 ("Windows 11 24H2 or newer"), README.md:110 (Home: "Yes."), `Platform/BuildInfo.cs:84` (`MinimumBuild = 26100`), `:96-99`, `docs/vm-test-plan.md`, `docs/TODO.md:21`.

  - 25H2 (26200) was never run.
  - Home was never run; the TODO keeps the Home check of `privacy.locationOff` open.
  - 24H2 Home and Pro stop getting updates today (`Is24H2EndOfUpdates`).
- **Failure:** a 1.0 says "supported" for builds and editions where catalog detection, Group Policy behavior and the edition conditions were never seen to work.
- **Fix:**
  - Run the core plan on 25H2 Pro and on 26H2 Home, and record the results in the repo.
  - Decide for 24H2: keep it with a "not tested" note, or raise `MinimumBuild` to 26200.
  - Publish the support matrix (build, edition, tested or not) in the README.
- **1.0 blocker:** yes (or narrow the claims).

## Medium

1.0 blockers are marked **[1.0]**. Each line gives the location, the problem and the fix.

### Engine and backups
- **M1. A read that throws during apply skips that action, and the result still says Applied. [1.0]**
  - Where: `Tweaks/TweakEngine.cs:384-385` (`var current = SafeRead(a); if (current is null) continue;`) and `:481`. The verify step checks only `done`.
  - Example: a tweak with a registry and a service action, where the service read fails. Only the registry value is written, and the result says Applied. The next scan shows Partial.
  - Fix: tell "read failed" apart from "target absent". Fail before the first write, or return Partial and name the skipped targets.
- **M2. Re-applying the power plan after drift makes undo leave the created plan behind. [1.0]**
  - Where: `TweakEngine.cs:468-469` overwrites `Applied` on every apply. On the second apply `Target()` finds "Tunero Gaming" by name, so `_created` is false and the kind becomes `scheme-existing` (`SystemActions.cs:212-213`).
  - Result: `RestoreIfUnchanged` passes `appliedPlanCreated = false`, and the plan stays in Power Options for good.
  - Fix: keep `scheme-created` when the earlier entry was created for the same GUID. Add a test: apply, switch plan, apply again, undo, plan gone.
- **M3. An untrusted backup file counts as "no backup", and undo then reports success. [1.0]**
  - Where: `BackupStore.cs:157` (`if (!File.Exists(file) || !Trusted(file)) return null;`), `TweakEngine.cs:518-521` (`new RevertResult(true, [], [])`), `Program.cs:43` (the result of `DefaultOwner.SetAdministrators()` is ignored), `SecureFolder.RemoveUntrusted` (`BackupStore.cs:523-549`).
  - When `SetAdministrators` fails, new backups are owned by the user, and three things follow:
    1. Undo restores nothing and says OK.
    2. A second apply records changed values as originals.
    3. The next start deletes the file.
  - Fix:
    - Treat an existing untrusted file like a damaged one: block, never absent.
    - At start, write a probe file and check its owner; refuse changes if that fails.
- **M4. A stored NIC action loses its case-insensitive dictionaries.** Where: `ExtendedActions.cs:104-125`. Undo of a disconnected adapter, or after a driver update, can reject the stored action. Fix: rebuild the dictionaries with `OrdinalIgnoreCase` after deserialization, and add a mixed-case round trip test. Still open from 2026-10-12.

### Platform, hardware and checks
- **M5. One hung extras part empties the whole extras section, and most checks then disappear. [1.0]**
  - Where: `Hardware/Probes/ExtrasProbe.cs:90` (`Task.WaitAll` of 17 parts, no limit per part), `HardwareScanner.cs:199`.
  - Any of these can hang and take the rest with it: an unreachable UNC path in a Run key with a signature check, a hung WLAN service, NVAPI `LoadSettings`, the Storage WMI query.
  - Result: F11, F14, F16, F24 to F28, A.apo, A.virtualization and others `yield break`, so the score rises instead of showing Unknown.
  - Fix: a `WaitAsync` limit per part that returns `default`, and Unknown from every check when `Extras` is null.
- **M6. WMI calls without a timeout. [1.0]** Where: `SetDns` (`ExtendedActions.cs`, already in TODO) and the `PS_MMAgent` read used by tweak detection **[WIP]**. Fix: `ConnectionOptions.Timeout`, `EnumerationOptions.Timeout`, `InvokeMethodOptions.Timeout`, or a `WaitAsync` limit.
- **M7. F21 counts `useplatformclock No` as a performance problem.**
  - Where: `Findings/Checks/FixChecks.cs:203` (key only). Its page says it "makes every time stamp query use a slower timer", which is untrue for No.
  - Fix: count only Yes, or show No as Info and change the page.

### Feature modules and updates
- **M8. The Startup page lists Windows' own COM-handler logon tasks as unknown and switchable. [1.0]**
  - Where: `Platform/SystemApi.cs:370` (only `<Exec>` actions are read), `Startup/StartupScanner.cs:179-189` (no filter for `\Microsoft\Windows\`), `:431`.
  - Tasks such as TextServicesFramework\MsCtfMonitor get no command, so the signature check finds nothing and "Hide Microsoft entries" does not hide them. Switching off MsCtfMonitor is the known cause of "cannot type in Start search".
  - The scan already drops `Microsoft\` tasks from F16 (`ExtrasProbe.cs:193`).
  - Fix: resolve a ComHandler CLSID to its InprocServer32 for the signature, make tasks under `\Microsoft\Windows\` read-only unless allowlisted, and check in the VM which tasks appear.
- **M9. A failed restart after a self-update leaves no runnable exe. [1.0]**
  - Where: `MainViewModel.cs:836-842`. The catch for IO, access and Win32 errors only shows a message. `Updater.Install` has already moved the running exe to `.old`, and `RollBack` runs only on a hash mismatch (`:843-848`).
  - Example: antivirus quarantines the new unsigned exe, or Smart App Control blocks it (unverified). The shortcut then points at nothing.
  - Fix: call `Updater.RollBack(exe)` in that catch when the file is missing or the start was blocked.
  - Related: the restart starts the new exe without `ProcessHardening.Apply` (`:834`).
- **M10. The update signing key has no rotation path. [1.0]**
  - Where: `Updates/UpdateSignature.cs:16-58`, `scripts/new-update-key.ps1`. One embedded key; if it is lost, every installed copy needs a manual update.
  - Fix: embed a list with an offline backup key now. This cannot be added later for copies already in the field.
- **M11. "Update all apps" runs `winget upgrade --all` elevated.**

## Top 5 refactors

### 1. A persisted-format contract (H3). About 1 day.
1. Add `Format` to `TweakBackup` and `PendingUndo`; refuse a newer format.
2. Commit golden fixtures (one per action type, a runtime definition, a pending undo) and a test that loads, resolves and reverts each one.
3. Pin the discriminators and target key formats in a test, with a CONTRIBUTING rule that they are never renamed.
4. Replace `TweakCatalog.Version` with a hash of the catalog.

This makes "undo survives every update" a tested promise, and lets the action classes be refactored safely after 1.0. `ChangeTransfer` already does this right (`ChangeTransfer.cs:41-42`) and is the model.

### 2. A Core `ChangeSession` (M27, H1, promise gaps 7 and 9). 2 to 3 days.
1. In Core: scan, facts, detection and plan in one snapshot.
2. `ApplyAsync`, `UndoAsync` and `ApplyFileAsync` take the `ChangeLock` themselves and wait for a running scan instead of refusing, which also fixes the class of bug behind H1.
3. `ChangeRunner` keeps only the dialogs; `CommandLineApply` shrinks to an adapter.
4. Add CLI verbs (`--export`, `--profile ... --apply-recommended`, `--include-preview`) with a test each.

This unblocks CLI parity with WinUtil and Sophia Script, the opt-in re-apply task, and the first tests of change orchestration.

### 3. `UpdateService`, `UninstallService` and `StartMenuService`, plus an App test project (M9, M20). 2 days.
1. Move `MainViewModel.cs:680-1087` into services behind a process launcher and shutdown interfaces. This also covers rollback on a failed restart and the hardened start at `:834`.
2. Create `tests/Optimizer.App.Tests` for `ChangeRunner`, Import, these services and the row state logic.

The update path is the riskiest untested code at 1.0, because a bug there can stop the fix from arriving.

### 4. One `ProcessLauncher`, a `PowerShellScript` builder and a fakeable streaming runner (M28). 2 days.
1. One launcher that resolves the System32 path, applies `ProcessHardening`, and handles timeout, encoding and logging.
2. One script builder with the `$?` and `$LASTEXITCODE` template.
3. `StreamingProcess` behind an interface in `ActionContext`.
4. An architecture test over `src/`: `Process.Start` only in the launcher and `Program.cs`.

This unblocks fakes for winget, the health tools and PresentMon, and gives the bulk uninstall of promise gap 2 one safe place to run uninstallers.

### 5. `IShell`, a page registry and a file split (M31, M20). 2 to 3 days, mostly mechanical.
1. Pages depend on an `IShell` interface (about 18 members), not on `MainViewModel`.
2. A page registry for construction, language, preload and navigation.
3. Split `MainViewModel` into Overview, Tweaks, Changes and Settings view models.
4. Put each class in `PageViewModels2.cs` in its own file.
5. Move the inline quick fixes and the winget exit codes to Core.
6. Split `AdvisorChecks.cs` by domain.

New areas from the promise gaps (a rules page, bulk uninstall, Autoruns delete and export) then cost one file and one registry entry, instead of six edits in a 2,000-line class.

Worth doing alongside: return structured target text from `Describe` instead of parsing English back (M29). It is cheap, and it halves the work for a third language.
