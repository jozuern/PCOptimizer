# Repository audit, 2026-10-10 (third pass)

Scope: the whole repository, read only, at commit fceac3e (version 0.4.11) plus the uncommitted working tree. No code was changed for this audit. A performance session was editing the working tree at the same time: App.xaml.cs, MainViewModel.cs, PageViewModels.cs, DohActions.cs, ReadCache.cs, ReservedStorageAction.cs, SystemActions.cs, TweakAction.cs, HardwareScanner.cs, ExtrasProbe.cs, SystemApi.cs and TweakEngine.cs. Items that audit lists as "not fixed" are marked "(known)" here and not counted again.

Method: six area reviews ran in parallel:
- tweak engine and persistence;
- platform, interop and security;
- diagnostics and tools;
- the WPF app;

- build, CI, tests and licensing.

A seventh review covered cross-cutting concerns (architecture, coupling, duplication, dependencies). ## Summary

The baseline is strong:
- **Tests:** `dotnet test -c Release --filter "Category!=Hardware"` passes, 677 of 677, with no warnings, on a de-DE machine. That run covered the working tree with the other session's edits. It compiles only Core and the tests, not Optimizer.App (see L-B8).
- **No real adapters in tests:** no non-Hardware test reaches a real registry, service or power adapter. The only exception is a read-only read of the common Startup folder (L-B5).
- **Layering:** Core has no WPF references.
- **CI:** actions are pinned to SHAs, tokens have least privilege, and release artifacts are signed and hashed.
- **Updates and DLL loading:** update integrity holds (ECDSA over version plus hash, canonical release links, no downgrade). DLL loading is restricted.
- **App UI:** all 55 `SymbolRegular` names exist. The EN and DE resx have the same 527 keys. No WPF-UI gotcha was found.
- **Catalog:** every Expert or boot-critical tweak is a preview, every value conflict is declared, EN and DE pages agree, and impact scores stay modest.

The remaining risk sits in four places:

1. **The rule on undocumented values.** One recommended tweak, and several more behind Settings switches, use values Microsoft does not name, without `undocumented`, `proof` or `preview` (H3, M14, M15). The rule from 2026-10-10 is not yet applied to the older catalog files.
2. **Undo fidelity over catalog versions and accounts.** A re-apply overwrites the stored undo action (H1). A backup can exist both per user and shared (M2).
3. **The elevation boundary and the startup trust model.**
   - Only one of several runtime diagnostics variables is refused (H4).
   - "Microsoft" is decided by a name prefix (M3).
   - Command lines are resolved differently from how Windows resolves them (M4, M5).
   - Elevated uninstall trusts script hosts (M6).
4. **Feature code that does not work as advertised.** The benchmark never returns frames (H2). The throttle check reports Ok without load (M8). Game libraries are not protected in the storage analyzer (M9).

## Architecture and cross-cutting observations

Numbers come from grep over `src/`.

- **Exceptions:** 123 `catch (Exception ex)` and `catch (Exception)` sites. 78 have no filter, and 34 of those do not bind the exception, so they cannot log it.
  - Silent catches include `TweakEngine.SafeRead` (an unreadable original quietly drops the action from the apply), `Reg.cs:18,41,54`, `FirmwareProbe.cs`, `CleanupEngine.cs` and `StorageAnalyzer.cs`.
  - Write paths throw `InvalidOperationException` with English text and raw tool output, which the UI shows verbatim in German.
- **Adapter bypasses:** code that touches the PC outside `ActionContext`:
  - the static `Reg` (53 uses in 14 files);
  - the static `StreamingProcess` (Winget, HealthTools, PresentMon, PageViewModels2);
  - its own runner in `StabilityProbe`;
  - `ProgramUninstaller`;
  - direct starts in `MainViewModel.cs:520, 918`.

  Page operations that change the system (uninstall, winget, SFC and DISM) can therefore only be tested on real hardware.
- **Four ways to run a process** (`SystemProcessRunner`, `StreamingProcess`, `StabilityProbe`, `ProgramUninstaller`) and two ways to call PowerShell: inline `-Command` in DohActions, SystemActions, CleanupEngine and QuickFixes, versus `-EncodedCommand` only in `Debloat.cs:88-91`. Only `StabilityProbe` uses `ArgumentList`.
- **No cancellation:** `IProcessRunner.Run` takes no `CancellationToken`. DISM component cleanup (up to 60 minutes) and capability or feature changes (up to 30 minutes) cannot be cancelled.
- **Blocking probes:**
  - `ExtrasProbe.cs:63, 91, 93` and `FirmwareProbe.cs:26` block with sync-over-async.
  - `ExtrasProbe.cs:100, 199` call `Task.WaitAll`.
  - `HardwareScanner.cs:41` compensates with a process-wide `ThreadPool.SetMinThreads(64)`.
- **Coupling between pages and the shell:** MainViewModel creates the pages, and the pages call back through `Owner` for 12 members. `TaskExtensions.cs:20` and `App.xaml.cs:58` find the view model through `Application.Current.MainWindow.DataContext`.
- **Duplication:**
  - Two Uninstall-list readers: `Hardware/Probes/InstalledPrograms.cs` and `Apps/Programs.cs:36-60`.
  - Copy-pasted DISM wrappers: `Tools/Capabilities.cs:29-84` and `Tools/OptionalFeatures.cs:58-114`.
  - Five JSON save routines with different durability; `HealthStore.SaveThrottle` is not atomic.
  - The Administrators and SYSTEM SIDs are defined in three places.
  - Three folder-tree delete routines.
  - Five copies of the cancel boilerplate in `PageViewModels2.cs`.
- **Namespace cycles:**
  - `TweakAction.cs:67-69` registers derived types that live in Startup and Tools.
  - Adapters call probes (`SystemApi.cs:180` uses `PowerProbe`).
  - `SecureFolder`, which `Program.Main` relies on, lives in `Backup/BackupStore.cs`.
- **Build hygiene:** there is no `.editorconfig`, no `AnalysisLevel` and no `TreatWarningsAsErrors`. 25 of 41 numeric `Parse`/`TryParse` calls take no culture (all integers). P/Invoke mixes 87 `DllImport` with 29 `LibraryImport`.
- **Dependencies:** LibreHardwareMonitorLib serves one opt-in feature, but it brings 6 of the 16 license entries into the elevated exe. Among them are System.IO.Ports with 17 `runtime.*` packages and the obsolete facade System.IO.FileSystem.AccessControl 5.0.0.

## Top 5 refactors

1. **One process-execution layer.** Covers M6 and L-D7 and the cancellation and PowerShell items above.
   - **What:**
     - Give `IProcessRunner` a request object: arguments as a list mapped to `ArgumentList`, timeout, `CancellationToken`, encoding, an optional line callback, and a launch-only mode.
     - Add `PowerShell.Run(runner, script, timeout)` that always uses `-EncodedCommand`.
     - Move `StreamingProcess`, `StabilityProbe`, `ProgramUninstaller`, Winget, HealthTools, the update restart and rstrui onto it.
   - **Why:** one place for quoting, hardening, encoding and cancellation, and page operations become testable with fakes.
   - **Effort:** 1 to 2 days. **Risk:** medium, because encodings and quoting differ per tool. Add fake-runner tests that check exact arguments, then run the VM plan.
2. **A startup trust model in one place.** Covers M3 to M7 and L-P1.
   - **What:** one `ImageResolver` that resolves command lines the way CreateProcess and the SCM do (shortest prefix, `.exe` appended, bare names through `SystemPath`, no alternate data streams, local drives only).
   - **What:** one `Publisher` check that compares exact names and the root of the chain.
   - **What:** one rule for Microsoft-signed launchers: a payload argument outside protected folders makes the entry Suspicious.
   - **What:** scanner, uninstaller and services all use these.
   - **Why:** the same trust question is answered slightly differently in four places today, and each gap is an elevation or hiding path.
   - **Effort:** 2 days. **Risk:** low to medium, because the logic is pure. Table-driven tests with the examples from M4 and M5.
3. **Split the large files and add `IPageHost`.**
   - **What:**
     - Move `PageViewModels.cs` and `PageViewModels2.cs` to one file per page under `ViewModels/Pages/`.
     - Move `AdvisorChecks.cs` (22 checks) into the existing domain files plus new `NetworkChecks`, `FirmwareChecks` and `HealthChecks` files.
     - Cut `MainViewModel.cs` into `UpdateViewModel`, a `ScanCoordinator` without UI types, `ChangesViewModel`, and Tweaks, Advisor and Overview view models. They talk to the shell through an `IPageHost` interface (ShowResult, Profile, Runner, OpenLink, Scan) and report errors through an injected `IStatusSink` instead of `Application.Current`.
     - Add a `CancellableOperation` helper for the five cancel copies.
   - **Effort:** half a day for the file moves at almost no risk. 2 to 3 days for MainViewModel at medium risk, because binding paths change. Check with `--screenshot` in both themes and languages, and with `--perf` before and after.
4. **Shared infrastructure helpers.**
   - **What:**
     - `JsonFile.Save<T>(path, value, durable)` and `Load<T>` to replace five save routines.
     - `RegistryKey?` extension methods (`Values()`, `SubKeys()`, `Int()`, `Str()`) to replace the static `Reg` and about 20 `!` suppressions.
     - `InstalledPrograms` built on `Programs.Read`.
     - A shared DISM base for Capabilities and OptionalFeatures.
     - Well-known SIDs and one tree delete in Platform, with `SecureFolder` moved to Platform.
     - Core helpers for the profile path, theme and rstrui launch, so the App stops reading the registry and starting processes itself.
   - **Effort:** 1 to 2 days. **Risk:** low.
5. **Analyzer baseline and error policy.**
   - **What:**
     - `.editorconfig` with `AnalysisLevel=latest-recommended`.
     - CA1305, CA1307, CA2016 and CA1031 as warnings.
     - NU1902 to NU1904 and `TreatWarningsAsErrors` in CI.
     - The control-character test from M1.
     - Policy: read paths may fall back but log with a filtered catch, starting with `TweakEngine.SafeRead`. Write paths throw a typed `SystemToolException(tool, exitCode, output)`. The UI maps it to localized text and keeps the raw output in the log.
   - **Effort:** 1 to 2 days. **Risk:** low if warnings are turned on first and fixed step by step.

Also worth doing: move LibreHardwareMonitor into its own `Optimizer.Sensors` assembly that only the App references (half a day, low risk). This keeps its dependencies out of Core and its tests.
